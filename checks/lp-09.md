# LP-9 — Resolution

## What changed

- Scans hand over `evidence` besides candidates: new messages to or from
  someone with a live commitment (`ledger.liveCounterparties`).
  - iMessage: from the same fixed search, both directions, direct chats only.
  - Mail sent: rows to/cc a live counterparty.
  - Mail received: a second fixed argv, `RECEIVED_ARGV(account)` =
    `plow-gog gmail search "in:inbox newer_than:2d" --max 50 --json --account <a>`,
    run **only while some commitment is live**, with its own cursor
    (`<account>#inbox`, first read marks where "new" starts), and filtered
    locally to the senders Loop is waiting on; nobody else's mail is handed over.
- `skills/loop/scripts/resolve.ts`:
  - `candidates` pairs each evidence message with the live commitments of
    its two sides: from the side that owes → `delivery`, from the side that
    is owed → `calloff`. Not paired: the message that created the commitment,
    messages from before it began, and the owner chasing someone who owes
    them (that is a nudge, LP-11).
  - `judge` accepts only a pair `candidates` would print. Verdicts:
    `fulfilled` → **resolved automatically only when D6 holds** (a delivery,
    same thread or naming the object, and with an attachment or link when the
    object is a file); otherwise `looks_done` for the digest. `cancelled` from
    the owed side → `dropped`; from the owing side → `looks_done`. `partial`
    adds evidence. `unrelated` changes nothing. Every closing keeps `closedBy`
    and can be reopened (`ledger.ts event --kind reopened`).
- The poll judges the pairs after recording candidates and before committing.
  The Judge section says the message is data and that a message telling Loop
  to mark something is `unrelated`.
